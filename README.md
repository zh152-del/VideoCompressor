# 视频压缩（VideoCompressor）

完全本地运行的 Android 视频压缩 App。不联网、不上传、不需要账号，所有处理都在手机本地完成。

- 最低支持：Android 8.0（API 26）
- 目标版本：Android 16（API 36）
- 不使用 Root、无障碍、悬浮窗、服务器、远程数据库

---

## 一、它解决什么问题

手机相册越用越大，但里面绝大多数视频其实**根本没有压缩空间**：

- 屏幕录制、直播录屏的视频码率本来就很低，再压只会更大
- 已经被压过一遍的老视频，二次压缩往往得不偿失
- 很多压缩工具是「无脑压完再说」，用户白等几分钟、耗光电、占空间，最后发现文件反而变大了

本 App 的核心思路是：**在开始编码之前就判断这个视频值不值得压**，不值得的直接跳过，不浪费任何时间和电量。

---

## 二、核心功能

### 1. 自动识别可压缩视频

启动后自动扫描相册视频，走系统 MediaStore 接口（不硬编码 `/DCIM`、`/Movies` 目录，兼容不同厂商的目录结构），把可压缩的视频自动加入任务队列。

### 2. 码率前置判定（避免反向压缩）

这是本 App 最核心的机制。

在**编码开始之前**，先读取原视频的码率，与当前压缩档位算出的目标码率比较：

```
如果 原视频码率 ≤ 目标码率 × 0.85
    → 判定「再压缩只会更大」，直接跳过，不编码
```

举例：某个视频原码率 20 kbps，标准档目标码率 400 kbps —— 这段视频已经压得不能再紧了，直接跳过，不浪费一秒时间。

如果设备或容器格式无法读出码率，App 不会瞎猜，而是退回到「压缩后按实际体积判断」的保守路径。

### 3. 三档质量 + 四档分辨率

| 质量档位 | 说明 |
| --- | --- |
| 高质量 | 接近原画质，体积中等下降 |
| 标准 | 日常观看几乎无差别，体积明显下降 |
| 高压缩 | 画质有可见损失，体积下降最多 |

| 分辨率 | 说明 |
| --- | --- |
| 原分辨率 | 不缩放 |
| 1080P / 720P / 480P | 只下调，绝不把小视频放大 |

档位经过实测校准：早期版本「高质量」档会给 1080P 算出 18.6 Mbps 的目标码率，比很多原视频本身还高，必然导致压完变大。现在三档的码率已收紧到合理区间。

### 4. 输出完整校验（原视频安全的核心保障）

压缩完成后，输出文件要通过**五道独立校验**，任何一项不过就直接丢弃结果、完整保留原视频：

| 校验项 | 内容 |
| --- | --- |
| 文件有效 | 存在、非空、体积合理 |
| 可解析 | 能被系统媒体框架正确解析 |
| 有视频轨 | 画面轨存在、时长合理、分辨率有效 |
| 元数据一致 | 画面方向、宽高比、时长与源一致，且分辨率**未被放大** |
| 体积收益 | 确实比原文件小，并达到用户设定的收益阈值 |

源视频与输出文件用**同一套探测逻辑**读取元数据，避免两边各自朝同一方向错位、比例反而「对得上」的错误被放过。

除了「无损」，还会检查**音轨是否丢失** —— 源视频有声音、输出却没声，这是最不能接受的问题，直接判失败。

### 5. 安全删除原视频

只有输出文件**完整通过全部校验**之后，才会执行删除原视频。

- Android 11+ 走系统官方的批量删除授权（**一次授权处理整批**，不是逐个弹窗）
- 任何一步失败都会 100% 保留原视频
- 用户也可以完全关闭「压缩后删除原视频」，改为只压缩、保留原文件

**任务状态机**（原视频安全性的形式化保证）：

```
PENDING ──► PROCESSING ──► VERIFYING ──► COMPLETED ──► (删除原视频)
INTERRUPTED ─► PENDING          （App 被杀 / 重启后恢复）

PROCESSING ──► FAILED     压缩失败，原视频保留
PROCESSING ──► CANCELLED  用户取消，原视频保留
PENDING    ──► SKIPPED    不安全（码率已足够低 / HDR / 无视频轨 / 编码不支持），原视频保留
VERIFYING  ──► COMPLETED_NO_GAIN                   压缩成功但没变小，保留原视频
COMPLETED  ──► COMPLETED_BUT_ORIGINAL_DELETE_FAILED 压缩成功但删除原视频失败
```

**关键约束**：先落库标记 `COMPLETED`，**最后**才删除原视频。绝不允许出现「原视频已删但状态还是 PENDING」的中间态。

### 6. 后台与息屏保护

- 压缩运行在**前台服务**（`mediaProcessing` 类型，符合 Android 15+ 官方媒体处理规范）
- 使用 `PARTIAL_WAKE_LOCK` 保证息屏后 CPU 继续运行
- App 在前台时自动保持屏幕点亮，避免息屏后系统合成器停摆导致编码卡死
- **电池 / 温度 / 充电状态守卫**：低电量、过热、未充电时自动暂停开新任务，但正在编码的视频会正常跑完并完整保存状态，不会半途丢文件

### 7. 设备状态守卫

| 检查项 | 行为 |
| --- | --- |
| 剩余存储空间 | 预检「预估输出体积 × 2 + 512MB 安全余量」，不足则停止 |
| 电量 | 低于设定阈值（默认 15%）停止开新任务 |
| 充电状态 | 可设为仅充电时继续 |
| 系统温度 | 过高时停止开新任务，避免损伤硬件 |

### 8. 扫描结果可追溯

扫描后会明确区分并展示：

- 本次新增了多少任务
- 跳过了多少、**分别是什么原因**（已在队列 / 低于体积阈值）
- 排除掉的「本 App 自己之前压缩生成的产物」数量（避免反复压缩自己的输出）

### 9. 玻璃拟态 UI

全 App 统一的玻璃卡片视觉语言：内容卡片、批量操作条、扫描结果条目共用同一套玻璃合成逻辑（模糊底图 + 半透明渐变 + 边缘高光），避免同一 App 出现两套卡片风格。

## 三、技术栈

| 项目 | 选择 |
| --- | --- |
| 语言 | Kotlin 2.0.21 |
| UI | Jetpack Compose + Material3 |
| 压缩引擎 | **Media3 Transformer 1.5.1**（系统硬件编码器） |
| 任务队列 | Room 2.7.0（状态持久化，App 被杀 / 重启可恢复） |
| 设置存储 | DataStore Preferences |
| 视频扫描 | Android MediaStore |
| 后台 | Foreground Service（`mediaProcessing`） |

### 为什么没有引入 FFmpeg

Media3 Transformer 完整覆盖了所需能力（重编码、降码率、调分辨率、H.264 输出、AAC 音频、保留音频与方向元数据），因此**不引入 FFmpeg**，从而规避：

- APK 体积膨胀（多 ABI 原生库）
- native library 崩溃风险
- GPL / LGPL 许可证问题
- 硬件编码在不同机型上的兼容性差异

输出统一为 **H.264 + AAC / MP4**，任何设备都能播放。

---

## 四、隐私与安全承诺

- **不上传**任何视频、文件名、缩略图、元数据
- 无账号系统、无广告 SDK、无统计 SDK、无云端服务器
- 无网络权限依赖，核心功能全部离线可用
- 唯一的数据删除动作发生在用户主动点击删除之后，且严格走系统官方媒体删除机制

## 五、构建

```bash
./gradlew :app:assembleDebug      # 调试包
./gradlew :app:assembleRelease    # 发布包（需配置签名）
```

环境要求：JDK 21、Android SDK 36、Gradle 8.11.1（AGP 8.7.3）。

`local.properties` 中的 `sdk.dir` 为本机 SDK 路径，不纳入版本管理。
